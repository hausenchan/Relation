# YYZ 增长组织与多 Agent 协同 PRD

文档状态：架构已确认，进入 Phase 1 准备

业务负责人：YYZ 项目负责人

适用范围：`YYZ/` 业务根目录、Codex 调优工作区、Relation 组织 Agent 中台

最后更新：2026-07-29

---

## 1. 背景

YYZ 当前由商务、商业化运营、数据分析、增长策略、流量运营和产品研发共同推进。未来希望从按岗位
分工逐步升级为产运研一体化的增长黑客模式：AI 承担高频分析、方案设计、资料准备和执行辅助，员工
围绕统一业务目标组织工作，并把稳定经验蒸馏为 Skill，最终发布到组织 Agent 中台。

`YYZ/` 原候选业务目录如下，现已按本 PRD 迁移：

```text
BdBudgetDev
BdTrafficDev
OptAds
OptDataAnlys
OptStratDgn
OptTraffic
ProdH5
ProdMiniTb
ProdMiniWx
ProdMiniZfb
ProdYYZ
```

这些目录表达了真实工作内容，但同时混合了部门、岗位、业务流程、产品系统和预算形态。如果直接让
每个目录永久对应一个 Agent，会产生职责重叠、上下文重复、频繁转交和多份事实源。因此需要先定义
稳定业务能力边界，再决定哪些能力值得成为 Agent、哪些只是 Skill、知识目录或产品子域。

---

## 2. 目标

1. 建立一个 YYZ 总调度 Agent，作为项目负责人和最终业务结果责任人。
2. 按稳定业务能力建立领域 Agent，不按当前人员岗位机械复制 Agent。
3. 明确商务、运营、数据、策略、产品和组织支持的责任边界。
4. 建立可审计的 Agent 间任务、数据、策略、审批、执行和结果回传协议。
5. 让 Codex 对话可以按任务实例化 Agent，而不是长期维护十个不断膨胀的固定对话。
6. 将成熟工作流沉淀为可评测 Skill，并发布到 Relation 组织 Agent 中台。
7. 保持数据真实、生产变更可控、关键策略有人审和结果可回滚。

## 3. 非目标

- 不用 Agent 数量模拟现有组织人数。
- 不让 Agent 未经审批直接修改媒体单价、预算切量、用户奖励或生产开关。
- 不把所有业务知识、运行进度和 Skill 内容堆入一个巨型 `AGENTS.md`。
- 不在 Git 中保存生产凭据、Cookie、个人敏感数据或未经脱敏的用户明细。
- 不在当前阶段为每个预算平台维护一套重复的常驻 Agent。

## 4. 核心设计原则

### 4.1 能力域优先于岗位

目录和 Agent 应描述长期稳定的业务能力，例如“预算供给拓展”“媒体增长”“数据智能”，而不是绑定
某个员工或当前部门名称。人员可以同时承担多个能力域，人员调整不应迫使 Agent 架构重建。

### 4.2 Agent、Skill、知识和产品域分开

| 对象 | 定义 | 典型例子 |
| --- | --- | --- |
| Agent | 能理解目标、规划步骤、调用工具/Skill、处理异常并交付结果的责任主体 | 数据智能 Agent |
| Skill | 输入输出稳定、可重复执行和评测的工作流 | YYZ 日报分析、媒体 ARPU 诊断 |
| 知识/契约 | 指标、字段、规则、SOP、模板和事实源定义 | DAU 口径、OrgSupportRequest 模板 |
| 产品域 | 被开发和运营的系统或预算接入形态 | YYZ 平台、支付宝小程序接入 |
| 对话 | 某个 Agent 为完成一次具体任务产生的运行实例 | 7 月 29 日大盘诊断 |

不是每个文件夹都必须运行一个 Agent。只有具备独立目标、决策权、输入输出、工具权限、评测标准和
足够任务量的稳定能力域，才升级为 Agent。

### 4.3 一个主 Agent，多 Skill 协作

一个任务对话只设置一个主 Agent，主 Agent 可以调用多个 Skill 或请求其他领域 Agent。这样能够明确
最终责任，避免多个 Agent 对同一结论争夺所有权。

### 4.4 数据与策略分离

数据智能 Agent 负责内部事实、口径、对账和归因证据；竞品情报 Agent 负责外部产品和市场证据；
增长策略 Agent 负责结合内外证据提出可证伪方案。策略 Agent 不得修改事实结论，情报和数据 Agent
也不直接替业务负责人决定是否上线策略。

### 4.5 生产动作需要审批

涉及预算、价格、奖励、投放、发布、合同、法务、财务和生产代码的动作，默认先生成方案或变更单，
经授权人员审批后再由对应执行方落地。

handoff，但不得默认给所有 Agent 复制一份进度文件。

## 8. 领域职责

### 8.1 预算供给拓展

- 寻找新的上游联盟、广告预算和任务供给。
- 评估计费方式、eCPM/CPC/CPA、容量、结算周期、核减规则和合规要求。
- 输出预算接入商业价值、目标媒体、预估收入和产品接入需求。
- 商务拓展完成后，把产品接入交给预算产品接入 Agent，把日常配置交给商业化运营 Agent。

### 8.2 媒体供给拓展

- 获取新的媒体 App、CID、入口和用户流量。
- 评估 DAU、用户画像、任务中心位置、接入方式、奖励体系和结算诉求。
- 定义商务方案、技术接入、验收数据、首期预算组合和上线计划。
- 媒体上线后，把日常增长责任交给媒体增长 Agent。

### 8.3 商业化运营

- 管理广告和任务配置，包括预算、广告位、媒体、CID、任务、成本单价、容量和上下线状态。
- 根据策略单执行可审批的配置动作，并记录变更前后值、审批人、时间和回滚方案。
- 监控上游预算消耗、收入确认、核减、回调和媒体结算。
- 为数据智能 Agent 提供可追溯的配置快照。

以下内容不再归商业化运营 Agent 独立负责：

- 软著、域名、平台账号、法务和财务：生成组织支持请求。
- 产品模板和公共前后端能力：交给预算产品接入或 YYZ 核心产品 Agent。
- 公司级研发资源：交给组织中台研发调度。

当前员工可以继续兼任这些工作，但要用不同任务类型和责任边界记录，不把多个能力合并成一个 Agent。

生产配置权限统一遵循
`YYZ/operations/monetization/production-change-policy.md`：Agent 可执行 L0 只读和 L1 草案，媒体单价、
预算比例、容量、任务排序、广告位、奖励和上下线属于 L2，由 YYZ 项目负责人审批、授权运营人员执行；
合同、法务、财务、域名、账号和生产代码属于 L3，增加对应组织审批。MVP 不授予 Agent 生产写权限。

### 8.4 数据智能

- 从平台、预算、媒体和用户四个维度交叉验证数据。
- 对收入、成本、毛利、毛利率、订单、DAU、申请 UV、完成 UV 和广告行为漏斗进行对账。
- 区分数据事实、证据支持的归因和待验证假设。
- 评估策略执行后的真实增量，不以自然波动代替实验效果。
- 对数据缺失、延迟、重复、口径冲突和异常回调独立告警。

### 8.5 竞品情报

- 研究任务聚合、激励平台、广告 SDK/H5 等 YYZ 直接和替代竞品。
- 研究支小、微小、淘小、百度 JS 等预算的替代产品、联盟和变现方案。
- 对比任务链路、广告位、奖励、eCPM、CPC、CTR、结算、核减和风控方式。
- 跟踪竞品版本、媒体合作、预算变化、推荐策略和商业模式。
- 输出竞品地图、产品拆解、预算基准矩阵、变化预警和可验证机会。
- 每项事实记录来源、采集日期、适用范围和置信度；不绕过访问限制或收集商业秘密。
- 不为每个竞品创建 Agent，竞品实例维护为分类知识档案。

### 8.6 增长策略

- 消费商业化配置、数据智能结论和竞品情报，设计预算分配、媒体分配、任务排序和产品链路策略。
- 优化广告位、展示方式、eCPM、CPC、CTR、有效点击率和广告负载。
- 设计核减、封控、结算完整性和上游收入确认策略。
- 当单订单收入高于单订单媒体成本时，设计在风险可控下扩大订单和平台毛利的方案。
- 输出保守、中性、乐观测算，以及成功标准和止损条件。
- 只提出和评审策略，不直接修改生产配置。

### 8.7 媒体增长

- 从已接入媒体的大盘角度提升媒体结算收入和 YYZ 毛利。
- 优化媒体内预算组合、任务排序、用户分群、奖励表达和完成深度。
- 提高 DAU 到完成订单的整体效率，重点关注每 DAU 完成订单和完成人均订单。
- 同时保护媒体收益、用户体验和平台毛利，不以短期广告堆叠损害长期留存。

### 8.8 预算产品接入

- 统一管理 H5、支付宝小程序、微信小程序和淘宝小程序等预算产品接入。
- 建设任务协议、跳转、回跳、回调、订单状态、广告行为和收入确认链路。
- 平台差异以子目录知识、配置和 Skill 表达，公共能力只实现一次。
- 新预算平台默认先作为子域接入；只有具备长期独立工具和任务量后才拆成新 Agent。

### 8.9 YYZ 核心产品

- 负责 YYZ 前端任务展示、后端任务下发、任务中心、用户画像和推荐能力。
- 逐步建设“任务版今日头条”：根据媒体、用户行为、兴趣、历史申请/完成、收益、容量和风险，
  向不同用户推荐更可能完成且单位经济模型健康的任务。
- 推荐目标不是单纯点击率，应联合优化完成概率、单订单毛利、用户留存、预算容量和媒体收益。
- 负责产品 PRD、埋点、实验、版本发布、回滚和效果复盘。

## 9. 指标边界

以收入 8000 元、媒体结算成本 3000 元、毛利 5000 元、DAU 20 万为例：

| 指标 | 公式 | 结果 | 用途 |
| --- | --- | ---: | --- |
| YYZ 收入 ARPU | `收入 / DAU` | 0.04 元 = 4 分 | 衡量每 DAU 贡献的平台收入 |
| 媒体结算 ARPU | `成本 / DAU` | 0.015 元 = 1.5 分 | 衡量媒体每 DAU 从 YYZ 获得的结算 |
| YYZ 毛利 ARPU | `毛利 / DAU` | 0.025 元 = 2.5 分 | 衡量每 DAU 贡献的平台毛利 |
| 变现 ROI | `收入 / 成本` | 2.67 | 衡量同口径收入对媒体成本的覆盖 |
| 毛利率 | `毛利 / 收入` | 62.5% | 衡量收入质量 |

“媒体 ARPU”在正式分析中必须明确是媒体结算 ARPU、YYZ 收入 ARPU 还是毛利 ARPU，禁止只写一个
含义不明的 ARPU。单订单 ROI 必须保证收入和成本使用同一批订单、同一时间归因和同一核减口径。

## 10. 标准协同流程

```text
员工提问 / 数据监控 / 经营目标
            |
            v
YYZ 增长总调度员：明确目标、范围、优先级和决策时限
            |
            +--> 数据智能：事实、对账、归因和置信度
            +--> 竞品情报：外部产品、预算基准、变化和机会
            +--> 商业化运营：当前配置、价格、容量和变更历史
            |
            v
增长策略：形成方案、影响测算、实验和止损条件
            |
            v
YYZ 总调度仲裁 + 必要的人工审批
            |
            +--> 商业化运营执行配置
            +--> 媒体增长执行运营动作
            +--> 产品 Agent 形成研发和发布任务
            +--> 商务 Agent 推进外部合作
            +--> 组织中台小智调度公司级支持
            |
            v
数据智能评估增量 -> 总调度复盘 -> Skill 蒸馏/迭代/回滚
```

### 10.1 协同约束

- Agent 间不依赖自由聊天转述关键事实，应通过结构化任务和结果传递。
- 总调度员拥有任务拆解和业务验收责任，不代替法务、财务或生产变更审批。
- 数据智能、竞品情报和策略 Agent 保持独立，策略方案必须引用已确认的内外部证据。
- 执行 Agent 只执行自己权限范围内的动作；越权事项转组织支持或人工审批。
- 所有策略执行后必须回到数据评估，不允许以“已上线”作为任务完成标准。

## 11. Agent 间任务契约

组织中台当前没有统一 Agent 任务协议。YYZ 先采用
`YYZ/shared/task-contracts/domain-task-request-v1.md`，Relation 后续建立统一协议时做字段映射，不让
每个领域 Agent 各自发明格式。

### 11.1 DomainTaskRequest

```yaml
schema: yyz.domain-task-request.v1
task_id: YYZ-20260729-001
parent_task_id: YYZ-ROOT-001
project: YYZ
requested_agent: yyz-data-intelligence
business_goal: 提升爱奇艺媒体毛利ARPU
scope:
  date_range: latest-complete-day
  media: 爱奇艺极速版
  budgets: [支小]
  comparison_windows: [D-1, last-7-days, last-30-days, last-week-same-weekday]
inputs:
  source_refs: []
expected_output: 媒体x预算归因和P0机会
acceptance_criteria:
  - 财务数据与维度数据完成对账
  - 所有关键数字附来源
priority: P1
deadline: 2026-07-30T18:00:00+08:00
permissions: read_only
requested_by: YYZ项目负责人
callback_to: YYZ总调度任务ID
```

### 11.2 AnalysisResult

数据结果至少包含：数据窗口、截止时间、事实源、关键数字、变化贡献、数据质量、事实、推断、待验证
假设、置信度和引用。不能只返回自然语言结论。

### 11.3 StrategyProposal

策略结果至少包含：目标、基线、假设、影响公式、保守/中性/乐观区间、执行步骤、负责人、审批要求、
成功标准、止损条件、观察周期和回滚方案。

## 12. 组织支持设计

### 12.1 是否建立 YYZ 子 Agent

软著、域名、平台账号、法务、财务和公司级研发支持不建立 YYZ 常驻子 Agent。它们属于跨项目组织
能力，应由 YYZ 总调度员生成结构化 `OrgSupportRequest`，交给组织中台小智继续路由。

YYZ 仍保留以下目录作为能力入口：

```text
YYZ/shared/org-support/
  service-catalog.md
  org-support-request-v1.md
  request-templates/
```

该目录保存服务目录、请求协议和模板，不保存组织侧完整 SOP，不设置独立 `AGENTS.md`。组织侧 SOP
和 Skill 应在组织 Agent 中台维护，YYZ 只持有引用，避免多个项目复制同一套流程。

### 12.2 当前人员兼任

当前负责广告运营的员工可以继续执行这些事项，但系统中应区分两种任务身份：

- 商业化运营任务：广告配置、单价、媒体、预算、监控和结算。
- 组织支持任务：软著、域名、账号、法务、财务和公司研发资源申请。

人可以兼任多个能力域，Agent 定义不需要和员工数量一一对应。当组织支持事项形成独立任务队列、
专用权限、固定 SLA 和跨项目复用需求后，应在组织中台建设 `Organization Enablement Agent`，而不是
在 YYZ 下私有化。

### 12.3 OrgSupportRequest

```yaml
request_id: ORG-YYZ-20260729-001
source_project: YYZ
source_task_id: YYZ-20260729-001
request_type: software_copyright | domain | platform_account | legal | finance | engineering
business_goal: 为什么需要该组织支持
deliverable: 需要交付的成果
inputs: 已准备的资料及文档引用
priority: P0 | P1 | P2
deadline: 期望完成时间
approver: 审批角色或人员
data_classification: public | internal | confidential
acceptance_criteria: 验收标准
callback_to: YYZ总调度任务ID
```

组织中台小智负责权限检查、路由、进度跟踪和结果回传；YYZ 总调度员负责确认组织支持是否真正满足
YYZ 业务目标。

组织中台当前没有统一任务协议，因此本阶段先以 `yyz.org-support-request.v1` 作为 YYZ 侧权威请求
格式；Relation 接入时映射为平台任务，并保留 `source_project`、`source_task_id` 和状态回调。

## 13. Codex 对话设计

### 13.1 Agent 与对话的关系

```text
一个 Agent 定义 -> 可以产生多个任务对话
一个任务对话 -> 只有一个主 Agent，可以调用多个 Skill
一个总调度对话 -> 可以创建或调度多个领域任务对话
```

十个 Agent 定义不等于永久打开十个对话。Agent 是可复用角色，对话是一次具体目标的运行实例。

### 13.2 长期对话

只建议保留一个长期总控对话：

```text
YYZ / 总调度 / 项目经营总控
```

该对话负责读取 `YYZ/AGENTS.md` 和 `YYZ/handoff.md`，维护项目目标、优先级、跨域任务和最终决策。
它不承载每次详细取数、长篇代码开发或单一媒体排查，避免上下文持续膨胀。

### 13.3 任务对话

领域对话按目标创建，而不是按 Agent 永久创建：

```text
YYZ / 数据智能 / 7月29日大盘诊断
YYZ / 数据智能 / 爱奇艺近30日结算ARPU
YYZ / 竞品情报 / 支小预算竞品扫描
YYZ / 商业化运营 / 支小广告位配置复盘
YYZ / 增长策略 / 支小核减控制方案
YYZ / 媒体增长 / 爱奇艺人均订单实验
YYZ / 预算产品接入 / 淘小V2回调改造
YYZ / 核心产品 / 任务推荐排序一期
```

### 13.4 新建与复用规则

继续复用同一对话的条件：目标、业务范围、数据窗口和主 Agent 基本一致，且上下文仍可控。

出现以下情况时新建对话：

- 目标从分析切换为产品开发或商务拓展。
- 媒体、预算、日期窗口或权限范围发生明显变化。
- 原任务已经验收，需要开展新的实验或下一阶段。
- 对话过长，旧结论和新事实开始相互干扰。
- 需要独立评测、独立产物或独立提交记录。

初期同时保持 3-6 个活跃工作对话较合理，不需要固定开满十个。预算拓展、媒体拓展、竞品专项和具体平台接入
按项目临时开启。

### 13.5 对话命名

```text
YYZ / <主Agent> / <具体目标> / <日期或版本>
```

例如：

```text
YYZ / 数据智能 / 7月29日大盘归因 / 2026-07-29
YYZ / 竞品情报 / 支小预算竞品扫描 / 2026-Q3
YYZ / 媒体增长 / 爱奇艺人均订单实验 / EXP-003
YYZ / 核心产品 / 推荐系统一期 / v0.1
```

### 13.6 对话启动模板

```markdown
主 Agent：yyz-data-intelligence
父任务：YYZ-ROOT-001
目标：定位爱奇艺媒体结算 ARPU 下降原因
范围：最近完整日，爱奇艺极速版，支小；对比 D-1、近 7 日、近 30 日和上周同星期
数据源：Mid-Max Part 1-3，只读
预期输出：完成对账的归因分析和前三个机会
验收标准：关键数字附来源，事实/推断/假设分开
写回位置：YYZ/outputs/... 或父任务结果
```

### 13.7 对话结束

领域任务结束后不复制完整聊天记录，只回传结构化结果、产物路径、数据引用、已知限制和下一步。
总调度员验收后更新 `YYZ/handoff.md`，成熟流程再进入 Skill 蒸馏。

## 14. Skill 沉淀与组织中台发布

### 14.1 Skill 来源

- 高频重复且输入输出稳定的人工流程。
- 多次获得高质量反馈的 Codex 对话。
- 有明确效果的增长实验和复盘。
- 可稳定读取的数据报表、API 和配置流程。

### 14.2 发布流程

```text
领域任务对话
-> Skill 候选
-> 固定评测集
-> 历史日期回放
-> 影子运行
-> 业务负责人审核
-> Relation AI 训练台发布
-> 员工使用与反馈
-> 业务效果评估
-> 迭代或回滚
```

### 14.3 评测维度

- 取数正确率。
- 指标口径正确率。
- 数字忠实度。
- 归因正确率。
- 策略可执行性。
- 权限和安全合规。
- 员工采纳率。
- 实际业务增量毛利。

### 14.4 `yyz-dashboard-analysis` 权威源码与发布

推荐采用“一个权威源码、两个运行发布面”，不在 YYZ、Gcad、`.codex` 和 Relation 中台同时手工
维护多份代码：

1. **权威源码**：
   `YYZ/intelligence/data-intelligence/skills/yyz-dashboard-analysis/`，与报表契约、评测集和领域
   Agent 共同演进。
2. **Codex 运行镜像**：`.codex/skills/yyz-dashboard-analysis/`，由同步/打包脚本从权威源码生成，
   禁止直接形成另一条修改分支。
3. **组织中台发布版本**：Relation AI 训练台通过 API 接收不可变包，记录 `skill_code`、语义版本、
   来源仓库、来源路径、提交号、校验值、评测结果和发布人。
4. **Gcad 边界**：Gcad 只保留已经抽象为跨业务、跨项目的岗位通用 Skill；YYZ 专属报表、指标和
   策略 Skill 仍以 YYZ 业务根目录为权威源。需要复用时通过包和版本引用，不复制源码。

`yyz-dashboard-analysis` 的 `0.1.0` 权威源码已经迁移到数据智能领域目录，并通过
`scripts/sync-yyz-dashboard-analysis.js` 单向生成 `.codex` 运行镜像。`manifest.json` 记录版本、归属、
源码、镜像、评测和发布状态；`npm run skill:check:yyz-dashboard-analysis` 校验文件差异和 SHA-256
树校验值。Relation 发布 API 尚未完成，当前状态仍为 Codex 候选 Skill，不能视为组织级已发布版本。

### Phase 0：架构确认

- 本 PRD 的能力域方向已确认。
- 十个 Agent 的目标目录和小写短横线命名已落地。

先建设高频核心能力：

1. YYZ 总调度 Agent。
2. 数据智能 Agent。
3. 商业化运营 Agent。
4. 增长策略 Agent。
5. 媒体增长 Agent。

`2026-07-28`，但执行前必须确认 Part 1-3 与财务事实源均已完整更新。如果该日仍有延迟，自动回退到
最近一个数据完整日。完成“分析 -> 策略 -> 审批 -> 执行 -> 评估”闭环。

- 以评测和真实业务结果持续迭代 Agent 与 Skill。

## 16. 验收标准

1. 目录按能力域组织，不再依赖当前人员岗位。
2. 十个 Agent 均有唯一目标、输入、输出、工具、权限和评测标准。
3. `OptAds` 原职责已拆成商业化运营、组织支持和产品任务。
4. 数据智能、增长策略、执行和评估形成完整闭环。
5. ARPU、ROI、收入、成本和毛利使用明确且一致的口径。
6. 组织支持通过结构化请求进入小智，不建立 YYZ 万能支持 Agent。
7. Codex 采用一个长期总控对话和按任务创建的领域对话，不固定维护十个对话。
8. Agent 间通过结构化任务和结果协议协作，关键事实不依赖聊天转述。
9. 生产变更具备审批、审计、监控、止损和回滚。
10. 成熟流程可以进入评测并发布到组织 Agent 中台。
